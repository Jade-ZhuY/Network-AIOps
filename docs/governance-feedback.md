# 治理反馈闭环

日期：2026-10-20。补齐问数路线的最后一层：**发现问题 → 留下治理记录 → 人工处理 → 审核/发布或澄清/修复 → 用真实查询验证 → 关闭；回归时重新打开**。

不是 SQL 示例缓存，不是自动训练模型，也不自动补造采集数据、扩大权限或执行修改 SQL。

## 入口与流程

左侧新增 **治理反馈**。调查报告出现“已记录治理反馈 · 查看”时，可进入对应记录。

1. 新的已登录 chat/resume 请求结束并保存后，自动收集数据源缺口、未支持的指标/查询方式、业务口径歧义、模型 SQL 待审核、问数规划/执行异常。
2. 相同问题和时区保守去重，累计请求记录。仅折叠连续空白及大小写，不做相似 SQL 检索或自动改写设备/日期/阈值。
3. 填写处理说明和可选处理人备注，设置“待处理 / 处理中 / 暂不处理”。处理人备注不授予账号权限，不发送通知。
4. 通过“打开调查 · 审核 / 发布”复用已有 [查询审核与正式指标](metric-review.md) 功能；治理记录自动关联审核历史、已发布指标和后续查询。
5. 提供实际成功请求 ID，选择相应验证方式、明确确认范围，点击 **验证并关闭**。失败的检查项会展示并记录，不返回假的“已解决”。
6. 新故障/未支持要求再次出现、闭环指标被改判撤回或更换版本时，相关已关闭记录会重新打开。

普通缺设备/时间、正常空结果、权限拒绝/写请求和纯知识检索不自动塞进指标治理队列。无状态 `/metrics/resolve`、demo analyze 没有持久请求归属，不自动生成治理记录。历史请求需使用“补收最近 20 条请求”或指定请求补收，没有启动后台扫描/定时任务。

## 三种验证方式

### 发布后的正式指标

```text
第三层 SQL 待核对
 → 人工确认结果正确
 → 明确确认口径并发布正式指标
 → 查询指标「名称或别名」 R3 昨天
 → 用新的成功请求验证闭环
```

检查：指标来自本治理项收集到的查询证据；指标仍有效、审核版本/定义指纹匹配；证明请求真实执行了该指标当前版本；结果完整、非空、未截断，实际执行时间晚于发布及最近问题。

发布本身不自动结案，原始模型 SQL 即使审核过也不是发布后重新取数。私有正式指标仍采用明确的名称/别名调用；**不声称原始自然语言问法已自动泛化命中**。再次以原问法触发未验证 SQL，会诚实地重新打开治理项。

### 原问题修复

修复采集/代码/内置指标能力后，重新执行相同问题和时区。证明请求必须第一层 hit、只读指标 SQL 成功、报告 completed、证据完整，不能用另一种含义的问题或未验证 SQL 替代。关闭的是已验证的问数能力问题，不是自动确认网络故障根因。

### 本次调查口径已澄清

例如原问题“查询 R2 昨天设备整体平均丢包率”存在歧义，随后在同一会话明确选择“先算每个接口均值，再按接口等权”。

验证会核对该会话保存的原歧义记录、设备/时间/指标/接口/分类条件保持一致、显式口径选择、第一层成功结果及真实执行时间。通过后仅关闭**本次已澄清的调查**，不把选择静默写成全局默认口径。再次提出歧义问题仍会澄清并重新打开记录。

## 不用旧结果掩盖回归

- 只有验证接口产生 `resolved`，普通状态更新接口不接受“已解决”。
- 失败、空结果、截断、未验证模型 SQL、不相关指标、非本人请求、旧指标版本、过期审核均不作证明。
- 每条 SQL 证据新增服务器生成的 `executed_at_utc`。它是实际执行时间，不是采样日期、`DEMO_NOW` 或请求保存时间。
- 问题再次出现后必须有新的执行证据。仅重放 checkpoint/resume、刷新保存时间，不会把旧成功结果变成新证明。旧证据没有执行时钟时需重新查询。
- 验证在证明会话锁和治理事务下进行，核对版本再写入状态；指标撤回与相关治理项重开也在同一文档事务中提交。
- “暂不处理”记录理由，但不计入已验证解决；新问题出现仍可重开。

## 存储与失败补收

复用应用状态 PostgreSQL 的 `aiops_metric_governance`，向原 JSONB 文档增量添加 `feedback_cases`。兼容此前只有 reviews/metrics 的记录，没有新业务 MySQL 表、没有新 SQL 缓存集合。若该状态表尚未建立，仍需此前的显式迁移 `uv run python -m scripts.migrate`。

治理记录只保留问题、原因码、处理/验证日志、请求引用、受限查询上下文和指标引用，不复制业务结果行或执行 SQL。每个用户/租户/完整 Scope 单独隔离，管理员不会因此看到其他人的记录。

业务请求先保存，再归档治理反馈；两个存储动作不伪装成跨表原子提交。归档失败时响应明确返回 `governance_feedback.capture_status=pending`，保留已保存的业务结果，并可按请求 ID 幂等补收。历史页面仍会展示待补收状态。请求存储本身失败则保留原有 503 行为，不假称调查已保存。

会话历史使用同一份治理快照装饰一批消息，避免每条消息重新传输一份较大的 JSONB 文档。不会在读取历史时重新执行 SQL。

上限：每身份 300 个治理项、每项 100 条请求引用、最近 100 条事件（保留历史总数），并共用原 8 MiB 文档预算。超限明确待补收/409，不悄悄丢事件。尚未包含跨团队共享、IAM 分派、定时重试或完整归档系统。

删除原会话不自动删除独立治理记录；原请求过期后打开/验证该请求会返回 404，需要新的有效证明。内存模式重启不保留，页面明确提示；`persistence_backend=none` 不开放治理接口。

## API

均需原有 Bearer 身份，客户端不接受 owner、tenant、scope、替换 SQL 或结果行。

- `GET /api/v1/governance/cases?status=open&kind=source_missing&offset=0&limit=30`：分页列表、各状态计数、存储模式。
- `GET /api/v1/governance/cases/{case_id}`：原因、请求、关联指标、处理历史、最近验证。
- `PATCH /api/v1/governance/cases/{case_id}`：CAS 更新处理状态与说明。

  ```json
  {"expected_revision":1,"status":"in_progress","assignee":"数据维护人","note":"补齐采集字段后重新验证"}
  ```

- `POST /api/v1/governance/cases/{case_id}/verify`：只核验已保存证据，不自动调用模型/执行 SQL。

  ```json
  {
    "expected_revision":5,
    "proof_request_id":"req_...",
    "resolution_kind":"published_metric",
    "metric_id":"reviewed_...",
    "note":"发布后已重新查询并核对指标定义与完整证据。",
    "confirm_scope":true
  }
  ```

  其他方式为 `original_query_fixed` / `clarification_confirmed`，`metric_id` 必须为 null/不填写。返回 `verified`、逐条 `checks` 和最新治理项；校验失败以 `verified=false` 留痕，不结案。状态/版本冲突 409，非本人/失效请求 404，输入越界 422。

- `POST /api/v1/governance/capture/{request_id}`：幂等补收单次已保存请求。
- `POST /api/v1/governance/collect?limit=20`：补收当前身份最近请求，最多 50 条，返回归档/待补收统计。

chat、请求详情、会话历史附加 `governance_feedback`，不改写原始报告和事实。
